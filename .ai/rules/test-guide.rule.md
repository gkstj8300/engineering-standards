# 구현 및 테스트 가이드라인

기능 구현·버그 수정 후 검증하는 기준이다. 프론트엔드·백엔드 등 모든 코드에 적용하며, 테스트 도구는 §2 표에 프로젝트 값으로 채운다.

## 1. 기본 원칙

- 구현 후 테스트 필수: 기능 추가나 버그 수정 후 의도대로 동작하는지 검증한다.
- 테스트 동반 작성: 단위 테스트는 구현과 동시에 또는 바로 뒤에 작성한다.
- 실패 케이스 포함: 성공 시나리오뿐 아니라 예외(빈 값·null·경계값·네트워크 실패·연결 끊김)를 설계에 포함한다.

## 2. 테스트 도구

프로젝트에 맞게 채운다. 정해지지 않은 칸은 `[TBD]`, 해당 없는 칸은 `-`로 둔다.

| 영역 | 단위·컴포넌트 | 통합 | E2E |
|---|---|---|---|
| 예: 웹 프론트엔드(React) | Vitest + React Testing Library | MSW(API Mock) | Playwright(핵심 플로우) |
| 예: 백엔드 | [TBD] | [TBD] | - |

- 커버리지 측정 대상(핵심 비즈니스 로직 경로): `[TBD]` (예: `src/entities/**`, `src/features/**`)
- 정적 분석(타입 검사·린트·포맷 검사)은 CI에서 필수로 실행한다(예: `tsc --noEmit`, ESLint, Prettier).

## 3. 체크리스트

### 3.1 정적 분석

- [ ] 구문 오류와 미정의 참조가 없다.
- [ ] 린트와 타입 검사를 통과한다.

### 3.2 단위 테스트

- [ ] 외부 의존성은 Mock·Stub으로 격리했다(예: 프론트엔드는 MSW).
- [ ] §2의 커버리지 측정 대상에서 커버리지가 80% 이상이다.
- [ ] 테스트 이름에 대상·조건·기대 결과가 드러난다(예: `test_<대상>_<조건>_<기대결과>`, `it('<조건>이면 <기대 결과>')`).

### 3.3 엣지 케이스

- [ ] null·undefined·빈 문자열·0·빈 배열을 처리한다.
- [ ] 인덱스 경계를 처리한다.
- [ ] 네트워크 지연·API 실패 시 에러를 처리한다(빈 상태·스켈레톤·재시도).
- [ ] 시계열 표시에서 데이터 결측·연결 끊김 구간을 0으로 채우지 않고 끊긴 구간으로 표현한다.
- [ ] 미지원 항목과 데이터가 0건인 신규 사용자·계정을 처리한다.

## 4. 기능 유형별 필수 검증

해당하는 기능이 있으면 검증한다. 기준 수치가 정해지지 않았으면 `[TBD]`로 두고 회귀 비교로 판단한다.

- 인증·권한: 인가는 서버가 강제하며 우회 경로가 없다. 토큰 만료·재발급이 동작한다. 권한 없는 기능이 UI에 보이지 않으며, 노출 여부는 클라이언트 추정이 아니라 서버가 준 권한으로 판단한다.
- 실시간 데이터: 갱신 주기, 지연·재연결 처리, 시각의 표시 시간대가 맞다.
- 수치·상태 표시: 단위·소수 자릿수 규칙과 경계값에 따른 상태 분기가 맞고, 라벨·색·순서가 화면마다 같다.
- 목록과 상태 전이: 확인·처리 같은 상태 전이, 중복 항목 처리, 정렬 기준이 맞다.
- 계산·예측 결과: 산출 시각과 대상 기간이 함께 표시되고, 값이 없으면 빈 상태로 보인다.
- 대용량 조회: 장기간·다항목 조회에서 렌더 지연이나 멈춤이 없다.

## 5. 응답 전략 (구현 요청 시)

1. 테스트 계획을 요약한다.
2. 코드를 구현한다.
3. 테스트 코드를 작성한다.
4. 테스트를 실행하고 결과를 보고한다. 실행할 수 없으면 그 이유와 남은 검증 방법을 밝힌다. 실행하지 않은 테스트를 통과했다고 보고하지 않는다.

## 6. 회귀

- 새 기능을 추가하면 기존 테스트가 깨지지 않는지 확인한다. 기존 기능을 고치면 영향을 받는 모듈의 테스트도 갱신한다.
- 테스트를 통과하지 못한 코드는 완성으로 간주하지 않는다.
