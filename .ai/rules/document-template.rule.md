# 문서 작성 규칙

Markdown 문서를 만들거나 고칠 때 따르는 규칙이며, 기본 템플릿(§4)을 포함한다.
목표는 정확한 정보를 빠르게 찾을 수 있게, 코드와 다른 문서의 현재 상태와 일관되게 전달하는 것이다.

## 1. 적용 범위와 우선순위

- 적용: 저장소의 모든 Markdown 문서(`*.md`). AI 에이전트 지침·규칙 파일(예: `AGENTS.md`, `CLAUDE.md`)도 포함한다.
- 제외: 외부에서 가져온 문서(예: `node_modules/`, `vendor/`), 도구가 자동 생성하는 문서
- 우선순위: 사용자 직접 지시 > 프로젝트의 문서 규칙·템플릿 > 본 문서

## 2. 기본 원칙

- 확인할 수 있는 원본(코드, 설정, 명세, 요구사항)을 바탕으로 쓰고, 확인하지 못한 내용은 사실처럼 쓰지 않는다(§5.3).
- 현재 상태와 제안·계획을 구분한다.
- 같은 정보는 한 곳에서만 관리한다(§6).
- 기존 문서 수정으로 해결되면 새 문서를 만들지 않는다(§3).
- 프로젝트에서 이미 쓰는 용어, 표현, 파일 구조를 우선한다.
- 분량보다 정확성, 찾기 쉬움, 가독성을 우선한다.
- 코드만 봐도 명확한 내용은 문서로 만들지 않는다.

## 3. 문서 생성

새 문서를 만들기 전에 순서대로 확인한다.

1. 같거나 비슷한 목적의 문서가 이미 있는가
2. 기존 문서를 고치거나 확장하는 것으로 충분한가
3. 프로젝트에 정해진 템플릿이나 문서 규칙이 있는가

- 파일명과 위치는 같은 종류 문서의 기존 관례를 따르고(예: `YYYY-MM-DD_<주제>.md`, `README.md`), 관례가 없으면 소문자 kebab-case를 쓴다(예: `api-gaps.md`).
- 작업 과정 기록이나 분석 보고서는 사용자가 요청했거나 작업에 필요할 때만 만든다. 다른 규칙이 생성을 요구하는 기록은 그 규칙을 따른다.

## 4. 기본 구조

별도 템플릿이 없으면 다음 섹션을 위에서부터 순서대로 둔다. `<…>`는 채울 자리다.

| 섹션 | 담는 내용 |
|---|---|
| `# <제목>` | 문서 제목 |
| `## 개요` | 목적과 적용 범위(필요하면 배경) |
| `## <핵심을 나타내는 제목>` | 가장 중요한 결론·규칙·사용 방법 |
| `## <상세를 나타내는 제목>` | 구조·절차·명세·예제 |
| `## 예외 / 주의사항` | 예외 조건, 제약사항, 잘못 적용하기 쉬운 내용 |
| `## 원본` | 바탕이 된 원본(§6.1) |
| `## 참고` | 함께 볼 문서 |

- `<핵심…>`, `<상세…>` 자리에는 `핵심 내용`, `상세 내용` 같은 일반 이름 대신 내용을 드러내는 제목(예: `## 설치`)을 쓴다.
- 필요 없는 섹션은 생략하고 필요한 섹션은 추가한다. 단, 다른 원본을 바탕으로 쓴 문서는 `원본`을 생략하지 않는다.
- 문서명, 버전, 작성일, 변경 이력 같은 메타데이터 표는 두지 않는다. 버전과 이력은 버전 관리 시스템(예: Git)이 관리한다.

## 5. 작성 형식

### 5.1 분량과 헤딩

- 한 문서는 150줄 이하로 유지한다(빈 줄과 코드 블록을 포함한 파일 전체 줄 수 기준). 넘으면 주제별로 나누고 링크한다.
- 에이전트가 세션 시작 시 불러오는 지침 파일은 각 도구의 크기 한도도 지킨다.
- H1(`#`)은 문서당 하나만 쓰고, 헤딩 레벨을 건너뛰지 않는다(H2 다음에 바로 H4를 쓰지 않는다).
- 한 섹션에서는 한 주제만 다루고, 결론과 제약사항을 섹션 앞부분에 둔다. 헤딩만 읽어도 전체 구조를 알 수 있어야 한다.

### 5.2 본문

- 한 문단에는 하나의 요점만 담고, 긴 문단보다 목록을 우선한다. 순서가 중요하면 번호 목록을 쓴다.
- 표는 2개 이상의 항목이 같은 속성(열)을 가질 때 쓰고, 첫 행은 헤더로 쓴다. 빈 셀은 `-`, 확인하지 못한 값은 `[TBD]`로 채운다.
- 표의 셀에는 한 문장 이하의 값만 넣는다. 여러 문장이나 목록이 필요하면 표 대신 목록을 쓴다.
- 코드, 명령어, 경로, 식별자는 inline code나 코드 블록으로 표시하고(코드 블록에는 언어 지정), 파일 구조는 tree 형태로 쓴다.
- 같은 설명을 여러 섹션에서 반복하지 않고 해당 섹션을 참조한다(예: `§6`).
- 굵은 글씨는 놓치면 안 되는 핵심어와 경고에만 쓴다. 장식 목적의 이모지·기호는 쓰지 않는다.
- 예제는 규칙을 이해하는 데 필요한 최소한으로 쓴다.

### 5.3 표기

- 확인하지 못했거나 정해지지 않은 내용은 `[TBD]`로 표시하고, 무엇이 미확정인지 함께 쓴다(예: `차트 라이브러리: [TBD]`).
- 용어는 문서의 주 언어로 쓴다. 원어가 필요하면 처음 나올 때 괄호로 함께 쓰고, API처럼 굳어진 용어는 그대로 쓴다.
- 날짜는 `YYYY-MM-DD` 형식으로 쓴다.

## 6. 원본과 SSOT

원본은 어떤 정보의 최종 기준이 되는 코드, 설정, 명세, 요구사항 또는 문서다. SSOT(Single Source of Truth)는 같은 정보의 원본을 하나만 둔다는 원칙이다.

- 작업 전에 관련 원본과 현재 구현을 먼저 확인한다.
- 다른 문서는 원본의 내용을 복제하지 않고 링크한다. 저장소 안은 상대 경로로, 밖은 URL로 링크한다.
- 원본 경로에 파일이 없으면 이동·이름 변경 여부를 저장소 검색으로 확인한다. 찾지 못하면 다른 파일로 대체하지 않고 사용자에게 알린다.
- 리뷰, 분석 결과, 작업 기록은 원본으로 명시되지 않은 한 원본으로 취급하지 않는다.
- 바이너리 파일(PDF, DOCX 등)이나 외부 명세를 Markdown으로 정리해도, 그 Markdown이 원본을 대체한다고 가정하지 않는다.
- 원본으로 볼 수 있는 자료끼리 내용이 다르면 임의로 하나를 고르지 않는다. 어느 쪽을 따를지 정할 수 없으면 충돌 내용을 `[TBD]`로 표시하고 사용자에게 확인한다.

### 6.1 원본 표기

`## 원본`에는 다음 형식으로 적는다.

- 저장소 안의 원본: 상대 경로 링크(예: `[요구사항 명세](../requirements/spec.md)`)
- 저장소 밖의 원본: 자료명, URL, 버전 또는 확인일(예: `결제 API 명세 v2.3 — https://example.com/docs (확인일 2026-10-01)`)

### 6.2 요약 문서

- 외부 자료나 큰 명세를 요약할 때는 요약 범위를 개요에 적는다. 원본 전체를 복제할 필요는 없지만, 범위 안의 정보는 원본과 일치해야 한다.
- 요약한 원본의 버전이나 확인일을 반드시 적는다(§6.1). 그래야 원본이 바뀌었는지 판단할 수 있다.
- 원본과 요약이 다르면 원본을 따른다. 원본이 바뀌면 요약 문서와 이를 참조하는 문서의 영향을 확인한다(§7.1).

## 7. 수정과 변경 영향

- 필요한 범위만 고치고, 관련 없는 섹션을 다시 쓰지 않는다.
- 작업 범위 밖이거나 수정 권한이 없는 파일은 고치지 않는다. 변경이 필요하면 위치와 이유를 사용자에게 알린다.

### 7.1 변경 영향 확인

다음 변경은 영향을 받는 문서, 테스트, 코드를 확인한다.

- 요구사항·정책, 시스템 동작, API·스키마·계약(Contract), 아키텍처·주요 구조의 변경
- 문서 이동, 이름 변경, 분리, 병합(§8)과 원본 변경
- 헤딩 문구 변경(앵커 `문서.md#헤딩`이 바뀐다), 식별자·필드명·경로의 철자 수정

오탈자 수정, 문장 다듬기, 서식 정리처럼 의미가 바뀌지 않는 변경은 다른 문서나 코드로 전파하지 않는다.

- 참조 관계가 있다는 이유만으로 고치지 않는다. 영향을 실제로 받는 문서, 테스트, 코드만 고친다.
- 영향이 연쇄되면 영향을 받는 쪽을 따라가며 확인하되, 확인한 파일은 다시 처리하지 않고 순환 참조를 반복해서 따라가지 않는다.

## 8. 이동 / 이름 변경 / 삭제

문서를 옮기거나, 이름을 바꾸거나, 지우기 전에 그 문서를 가리키는 참조를 모두 찾는다.

- 저장소 전체에서 파일명을 검색한다. 확장자를 뺀 이름, 상대 경로, 앵커가 붙은 링크도 포함한다.
- Markdown 링크가 아닌 참조도 확인한다(예: `CLAUDE.md`의 `@AGENTS.md` 같은 불러오기 지시, 설정 파일, 코드 주석, CI 스크립트).
- 참조가 남아 있으면 새 경로로 갱신하거나, 새 원본으로 옮기거나, 필요 없어진 의존 관계를 제거한다. 참조가 깨진 상태로 옮기거나 지우지 않는다.

## 9. 민감정보

다음은 실제 값으로 쓰지 않는다. 형태를 설명할 때는 `<NAME>` 형식의 placeholder를 쓴다(예: `DATABASE_URL=postgres://<DB_USER>:<DB_PASSWORD>@<DB_HOST>/<DB_NAME>`).

- 인증 정보(비밀번호, API 키, 액세스 토큰, 개인 키 등)와 환경별 비밀 값
- 계정 정보가 들어간 연결 문자열, 비밀 값이 들어간 URL(Webhook URL, 서명된 URL 등), 세션 쿠키
- 실제 사용자·고객의 개인정보(연락처, 주민등록번호 등)

이미 노출된 민감정보를 발견하면 다음 순서로 처리한다.

1. 실제 값을 다시 출력하거나 복사하지 않고, 위치(파일 경로와 줄 번호)만 사용자에게 알린다.
2. 현재 파일의 값을 placeholder로 바꿀지 사용자에게 확인한다.
3. 값이 저장소 이력에 남았을 수 있으므로 값 교체(rotation)를 권고한다. 이력 재작성(예: Git force push)은 사용자의 명시적 승인 없이 하지 않는다.

## 10. 완료 체크리스트 (모든 항목이 "예"여야 완료)

- [ ] 개요나 첫 문단에 목적과 적용 범위가 있고, 그 범위에 필요한 정보가 빠지지 않았다.
- [ ] 150줄 이하이고, H1이 하나이며, 헤딩 레벨을 건너뛴 곳이 없다.
- [ ] 같은 설명이 여러 섹션에 반복되지 않고, 다른 문서에 있는 정보는 복제하지 않고 링크했다.
- [ ] 내용이 코드, 설정, 원본과 일치하고, 현재 상태와 계획·제안이 섞여 있지 않다.
- [ ] 확인하지 못한 내용과 해결하지 못한 충돌은 `[TBD]`로 표시하고 사용자에게 알렸다.
- [ ] 다른 원본을 바탕으로 쓴 문서에 `## 원본`이 있고(§6.1), 모든 링크와 경로가 실제로 존재한다.
- [ ] 같은 정보를 쓰는 다른 문서와 충돌하지 않고, 기존 용어와 구조를 이유 없이 바꾸지 않았다.
- [ ] 새 문서는 §3의 확인을, §7.1에 해당하는 변경은 영향 확인과 반영을 거쳤다.
- [ ] 실제 비밀 값이나 민감정보가 없다.
