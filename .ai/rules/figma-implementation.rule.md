# Figma node-id 기반 UI 구현 규칙

Figma MCP로 node-id를 추적하며 UI 컴포넌트·페이지를 구현할 때, 디자인에서 벗어나거나 임의로 판단하지 않도록 하는 규칙이다. 프론트엔드 UI 구현에만 적용한다.
R·P 번호는 [frontend.rule.md](frontend.rule.md)의 규칙과 프로필 슬롯이다.

## 1. 시작 조건

- 대상 Figma 파일(fileKey)과 디자인시스템 색인 문서(토큰·컴포넌트 node-id 목록)는 프로필 P16에 적는다.
- P16의 Figma 파일이 정해지지 않았으면 디자인 기반 구현을 임의로 시작하지 않는다. 사용자가 node를 지정한 URL을 준 경우에만 §4 절차로 진행한다.

## 2. 절대 원칙 (D1~D6)

위반하면 즉시 멈추고 사용자에게 보고한다.

- **D1 디자인 이탈 금지**: 색·타이포·간격·크기·radius·그림자·레이아웃·계층·상태를 node 데이터와 스크린샷 그대로 반영한다. 눈대중이나 근사치로 맞추지 않고, 요소를 재배치하거나 정렬·크기를 임의로 바꾸지 않는다.
- **D2 임의 판단·창작 금지**: 디자인에 없는 값·요소·상태·문구·아이콘·애니메이션·hover 효과를 추측해 추가·삭제·치환하지 않는다. 데이터가 없는 영역을 더미 데이터로 채우지 않고 디자인의 빈 상태를 따른다.
- **D3 디자인 토큰 우선**: Figma 변수를 프로젝트 디자인 토큰(P7)으로 매핑해 쓴다. 임의 hex·px 하드코딩을 금지한다(R9). 배경 투명도는 R12를 따른다.
- **D4 공용 컴포넌트 재사용**: 디자인시스템 배리언트(Button·Chip·StatusTag 등)는 공용 컴포넌트(P8)로 구현한다. 인라인 재구현을 금지한다(R10).
- **D5 추적성 유지**: 구현한 컴포넌트와 PR에 출처 node-id를 남긴다. 주석 형식은 `// figma: <node-id> <컴포넌트 경로>`다(예: `// figma: 23:15 Button/Primary/Large`).
- **D6 불명확·괴리 시 임의 결정 금지**: 디자인에 없거나 모순되면 §6 절차를 따른다. 추측으로 채우지 않는다.

## 3. node-id 추출

- URL `figma.com/design/<fileKey>/<name>?node-id=1-2`에서 fileKey는 `<fileKey>`, nodeId는 `1:2`다(URL의 `-`를 `:`로 바꾼다). `/file/` 형식 URL도 같다.
- 브랜치 URL(`.../design/<fileKey>/branch/<branchKey>/<name>`)은 `<branchKey>`를 fileKey로 쓴다.
- node-id가 없는 URL이면 진행하지 말고 node를 지정한 URL을 요청한다. 페이지 전체를 대상으로 가정하지 않는다(D2).
- 토큰과 공용 컴포넌트는 URL보다 디자인시스템 색인 문서(P16)의 node-id를 우선한다.

## 4. MCP 조회 절차 (순서 준수)

프로젝트에 설정된 Figma MCP 서버를 쓴다. 도구 이름은 서버마다 다르므로 목적에 맞는 도구를 고른다(예: figma-developer-mcp의 `get_figma_data`, `download_figma_images`). 각 단계의 목적은 추측이 아니라 데이터 확보다.

1. 구조 파악: 대상 node의 레이어 트리·이름·타입·크기·위치를 조회한다.
2. 정밀 스펙: 필요한 하위 node의 색·타이포·간격·오토레이아웃·제약을 node 데이터로 확정하고, 스크린샷으로 시각 대조한다.
3. 토큰 확인: 색·타이포·간격이 어떤 변수(토큰)인지 확인해 프로젝트 토큰과 매핑한다(D3). 매핑할 토큰이 없으면 §6을 따른다.
4. 자산 추출: 아이콘·이미지는 MCP로 내려받아 쓴다(벡터는 SVG). 스크린샷을 잘라 쓰지 않는다.
5. 응답 크기 관리: node 데이터가 크면 대상 nodeId로 범위를 좁혀 조회한다. 파일 전체를 무분별하게 조회하지 않는다.

## 5. 구현 절차

1. 매핑 확정: 구현할 화면·컴포넌트와 Figma node-id를 짝지어 기록한다. 화면 설계 문서가 있으면 화면 ID도 함께 기록한다.
2. 토큰·컴포넌트 매핑: 색·타이포·간격은 디자인 토큰으로, 배리언트는 공용 컴포넌트로 매핑한다. 새 컴포넌트가 필요하면 디자인시스템 정의 그대로 만들고 색인 문서에 등록한다(§6).
3. 레이아웃 재현: 오토레이아웃(방향·gap·padding·정렬·sizing)을 그대로 flex·grid로 옮긴다. 반응형은 디자인에 정의된 뷰포트만 대응한다.
4. 상태·접근성 구현: 디자인에 정의된 상태만 구현한다(예: Button Default·Hover·Active·Disabled). 디자인의 텍스트와 의미를 접근성 속성(라벨·역할)으로 반영한다. 키보드 focus 표시처럼 접근성에 필요한 상태가 디자인에 없으면 임의로 만들지 말고 §6으로 확인한다.
5. 검증: 구현 스크린샷과 Figma 스크린샷을 대조하고 §7 체크리스트를 확인한다.

## 6. 불명확·괴리 처리

디자인에 값이 없거나, node 데이터와 스크린샷이 모순되거나, 대응하는 토큰·컴포넌트가 없을 때 다음 순서를 따른다.

1. 임의로 결정하지 않는다(D6).
2. 무엇이 불명확한지 node-id와 함께 사용자에게 확인을 요청한다.
3. 확정 전까지 해당 부분은 구현을 보류하거나, 합의한 임시 처리를 코드와 PR에 명시한다. 추측으로 완성하지 않는다.
4. 디자인시스템에 반영할 새 토큰·컴포넌트는 디자인시스템 색인 문서(P16)에 등록한 뒤 사용한다.

## 7. 체크리스트 (구현 PR 전)

- [ ] 모든 색·타이포·간격·radius가 디자인 토큰으로 표현됐다(하드코딩 0).
- [ ] 공용 컴포넌트를 재사용했고, 배리언트·상태가 디자인과 일치한다(정의되지 않은 상태 없음).
- [ ] 오토레이아웃(gap·padding·정렬·sizing)을 그대로 반영했고, 정의된 뷰포트만 대응한다.
- [ ] 아이콘·이미지는 Figma에서 추출한 자산이다(스크린샷 크롭 아님).
- [ ] 접근성 속성(라벨·역할)이 디자인의 텍스트와 의미를 반영한다.
- [ ] 출처 node-id를 주석과 PR에 남겼다.
- [ ] Figma 스크린샷과 시각 대조를 마쳤고, 임의 추가·변경이 없다.
