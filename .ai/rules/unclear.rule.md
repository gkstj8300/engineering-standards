# 모호한 지시 처리 규칙

사용자 지시에 검증할 수 없는(모호한) 표현이 있을 때 에이전트가 따르는 절차다. 작업 종류와 관계없이 모든 지시에 적용한다.

## 1. 원칙

- 모호한 표현을 임의로 해석해 작업하지 않는다. 구체적인 기준을 사용자에게 확인한다.
- 질문하기 전에 프로젝트 규칙과 이전 명확화 기록(§4)에서 기준을 먼저 찾는다. 기준이 있으면 그 기준을 제안하며 확인한다.
- 모호한 부분만 묻고, 질문에는 고를 수 있는 구체적 기준 예시를 함께 제시한다.
- 사용자가 판단을 위임하면("알아서 해") 진행하되, 적용한 기준을 결과와 함께 밝힌다.

## 2. 검증 가능한 지시

예/아니요로 준수 여부를 판단할 수 있는 지시다. 다음 요소 중 하나 이상을 포함한다.

| 요소 | 뜻 | 예 |
|---|---|---|
| 수치 | 줄 수, 개수, 횟수, 시간 등 숫자 기준 | 파일당 200줄 이내 |
| 패턴 | 명명 규칙, 구조, 파일 위치 등 형태 기준 | 상수는 `UPPER_SNAKE_CASE` |
| 조건 | "~하면 ~한다"처럼 트리거와 동작이 명확함 | 외부 API 호출은 try-catch로 감싼다 |

## 3. 되묻기 예시

| 사용자 지시 | 판정 | 에이전트 행동 |
|---|---|---|
| "깔끔하게 작성해" | 모호 | "깔끔함의 기준이 무엇인가요? (예: 파일당 200줄 이내, 함수당 30줄 이내)" |
| "적절히 에러 처리해" | 모호 | "어떤 범위를 어떻게 처리할까요? (예: 외부 API 호출은 try-catch 필수)" |
| "좋은 구조로 만들어" | 모호 | "좋은 구조의 기준이 무엇인가요? (예: 파일당 단일 책임, 폴더 3단계 이내)" |
| "성능 좋게 해줘" | 모호 | "어떤 성능 기준인가요? (예: LCP 2.5초 이내, 번들 200KB 이내)" |
| "목록을 실시간으로 갱신해" | 모호 | "갱신 주기와 방식이 무엇인가요? (예: 30초 폴링, SSE 수신)" |
| "중요한 항목은 눈에 띄게 표시해" | 모호 | "어떤 기준과 표현인가요? (예: 마감 3일 이내는 경고 색과 아이콘)" |
| "파일당 200줄 이내로 작성해" | 검증 가능 | 바로 작업한다 |
| "컴포넌트 3개로 분리해" | 검증 가능 | 바로 작업한다 |
| "이미지는 공용 `Image` 컴포넌트로 렌더링해" | 검증 가능 | 바로 작업한다 |
| "마감 3일 이내 항목은 경고 색으로 표시해" | 검증 가능 | 바로 작업한다 |

## 4. 명확화 기록

되물은 뒤 사용자의 답을 기록으로 남긴다. 다음에 비슷한 지시가 오면 참고하고, 사용자가 자신의 판단 기준을 돌아볼 수 있게 한다.

### 4.1 기록 위치

- 폴더: 프로젝트에 정한 위치. 없으면 `docs/logs-clarifications/`
- 파일명: `YYYY-MM-DD_<주제>.md` (예: `2026-05-07_에러처리-기준.md`)
- 같은 날 같은 주제면 기존 파일에 항목을 추가하고, 주제가 다르면 새 파일을 만든다.

### 4.2 기록 형식

파일마다 H1은 하나만 두고, 확인한 지시마다 H2 항목을 추가한다. 날짜는 파일명에 있으므로 따로 적지 않는다.

```markdown
# 명확화 기록: <주제>

## <원래 지시 요약>

### 원래 지시
<사용자의 원래 표현>

### 모호한 부분
<검증할 수 없던 부분>

### 에이전트 질문
<되물은 내용>

### 사용자 응답
<사용자가 구체화한 기준>

### 확정된 규칙
<최종 적용한 검증 가능한 규칙>
```

### 4.3 기록 활용

- 비슷한 모호 지시가 다시 오면 기존 기록을 근거로 "이전에 이렇게 정하셨는데, 이번에도 같은 기준을 적용할까요?"라고 묻는다.
- 이전 기록만 근거로 임의 적용하지 않는다. 반드시 확인한다.
