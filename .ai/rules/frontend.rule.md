# 프론트엔드 코딩 규칙 (Core + Project Profile)

프론트엔드 코드를 작성·수정할 때 따르는 스택 무관 이식형 코딩 규칙이다. 적용 소스 범위는 프로필 P2의 경로 glob이며, 백엔드·인프라 등 비활성 영역에는 적용하지 않는다.

## 1. 구성

- Core(§1~§5): 스택과 무관한 원칙. 이식할 때 수정하지 않는다.
- Project Profile(§6): 프로젝트별 가변값(스택·경로·토큰·컴포넌트 등)을 채우는 유일한 편집 구역. 값이 필요한 규칙은 하드코딩 대신 슬롯 ID(`P1`~`P17`)를 참조한다.
- 프론트엔드 모듈 규칙: [frontend-architecture.rule.md](frontend-architecture.rule.md), [code-organization.rule.md](code-organization.rule.md), [figma-implementation.rule.md](figma-implementation.rule.md). 이 규칙들의 프로젝트 값도 §6 프로필에 적는다.
- 공통 규칙(프론트엔드 밖에도 적용): [code-comments.rule.md](code-comments.rule.md), [test-guide.rule.md](test-guide.rule.md), [unclear.rule.md](unclear.rule.md), [document-template.rule.md](document-template.rule.md)

## 2. 절대 규칙 (A1~A4)

위반하면 즉시 멈추고 사용자에게 보고한다. 프로젝트별 채택 여부와 예외는 프로필 P14에 적는다.

- **A1**: 실 API를 연동하면 Mock·하드코딩 폴백을 같은 커밋 또는 PR에서 모두 제거한다. "나중에 정리"는 금지한다(Mock 위치는 P11).
- **A2**: UI·UX 변경은 사용자가 요청할 때만 한다. 카테고리·라벨·레이아웃·항목 수를 임의로 줄이거나 합치지 않는다. 데이터가 없으면 임의 값으로 채우지 않고 빈 상태로 둔다(R19).
- **A3**: API 갭(엔드포인트·필드 누락)은 임의 Mock 대신 프로필 P12 문서에 등록한다.
- **A4**: 화면이 완성되기 전(디자인대로 구현하고 사용자가 확인하기 전)에는 계획·문서·코멘트에 백엔드(엔드포인트·매핑) 내용을 넣지 않는다. A3 갭 문서와 R15 데이터 문서는 예외다.

## 3. 핵심 컨벤션 (R1~R20)

값이 필요한 규칙은 참조 슬롯을 표기한다. 프레임워크·상태 규칙(R5~R8)은 React 계열 기준이며, Vue 등 다른 프레임워크는 P5에 같은 뜻의 규칙으로 바꿔 적는다.

| 그룹 | # | 규칙 | 참조 |
|---|---|---|---|
| 환경·스택 | R1 | 빌드·렌더 모드에서 금지된 런타임 API를 쓰지 않고, dev 전용 코드가 운영 빌드에 들어가지 않게 한다 | P3 |
| 환경·스택 | R2 | 타입 안전: escape hatch(강제 단언·무시 지시자·검증 없는 any) 금지, 부득이하면 unknown 후 좁힘, 타입 전용 import 사용 | P15 |
| 환경·스택 | R3 | 상태·이벤트·브라우저 API가 필요한 최소 단위만 클라이언트·동적 경계로 분리한다 | P5 |
| 환경·스택 | R4 | 내부 모듈은 경로 별칭을 쓰고, 깊은 상대 경로(`../../../`)를 쓰지 않는다 | P4 |
| 프레임워크·상태 | R5 | 프레임워크 반응성 규칙(Hook 최상위 호출, 정확한 의존성 배열 등)과 지정 린트 규칙을 지킨다 | P5 |
| 프레임워크·상태 | R6 | 새 컴포넌트는 프로젝트 표준 방식(예: 함수형)으로만 만든다 | P5 |
| 프레임워크·상태 | R7 | 트리를 넘는 공유 상태는 전역 스토어·URL 파라미터로 두고, props drilling은 컴포지션(children)으로 먼저 없앤 뒤 안 되면 Context·스토어로 분리한다 | P6 |
| 프레임워크·상태 | R8 | 데이터 로딩·라우트 파라미터·lazy 경계는 프레임워크 관용구대로 감싼다 | P5 |
| UI·토큰 | R9 | 임의 hex·arbitrary spacing을 쓰지 않고, 정의된 디자인 토큰만 쓴다 | P7 |
| UI·토큰 | R10 | 같은 용도의 공용 컴포넌트가 있으면 반드시 재사용하고, 인라인으로 다시 만들지 않는다 | P8 |
| UI·토큰 | R11 | 차트는 단일 라이브러리·토큰 색·의미별 고정 색을 쓴다(차트가 없으면 N/A) | P9·P7 |
| UI·토큰 | R12 | 배경 투명도는 프로젝트 정책을 따른다 | P10 |
| API 연동 | R13 | Mock은 격리된 폴더·이름 규칙에 둔다(제거 시점은 A1) | P11 |
| API 연동 | R14 | API 갭이 있으면 UI는 빈 상태·스켈레톤으로 두고 PR에 명시한다(갭 등록은 A3) | P12 |
| API 연동 | R15 | to-be 데이터 스펙과 as-is API 매핑 문서를 분리해 관리한다 | P13 |
| 코드 품질 | R16 | 의미 있는 이름: 축약·연속 숫자 금지, 도메인 용어 사용, 같은 개념은 같은 이름 | - |
| 코드 품질 | R17 | 매직 넘버·반복 문자열은 상수로 분리한다(1회성 라벨은 예외, 가독성 우선) | P15 |
| 코드 품질 | R18 | 기본 무주석, 쓸 때는 WHY만(제약·불변식·버그 우회, 상세는 [code-comments.rule.md](code-comments.rule.md)) | P15 |
| 코드 품질 | R19 | 부분 실패·빈 배열·null·로딩 상태를 분기(빈 상태·스켈레톤)하고, 값이 없으면 0·더미로 채우지 않는다 | - |
| 코드 품질 | R20 | 분리 기준은 길이가 아니라 단일 책임(도메인 로직이 섞이면 helper로, 같은 패턴이 3회 반복되면 하위 컴포넌트로 분리하고, 책임이 하나면 길이만으로 나누지 않는다) | - |

## 4. 우선순위 (충돌 해소)

1. 사용자 직접 지시
2. 절대 규칙(§2 A1~A4, P14)
3. 로컬 프로젝트 규칙(P15)
4. 본 문서 §3 R1~R20
5. P1 스택의 공식 모범 사례
6. 일반 프론트엔드 모범 사례

본 문서는 이식되는 규칙이므로 로컬 프로젝트 규칙(3)이 본 문서 컨벤션(4)보다 우선한다.

## 5. 채택 가이드

1. 규칙 세트 복사와 에이전트 연결은 [README](../README.md)를 따른다.
2. §6 프로필의 슬롯을 채운다. Core(§1~§5)는 수정하지 않는다.
